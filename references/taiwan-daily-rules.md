# 台股當日資料與操作檢查

適用於台股商品分類、交易單位、漲跌停與參考價的取得及使用，也適合排查資料已取得、程式卻持續等待的問題。08:00 補查是台股應用可採用的排程範例。採用前先確認各資料項目的適用交易日、有效期間與來源，並保留策略原有的操作授權。

## 先查 API，再判斷是否真的缺資料

先定位程式缺哪個欄位、目前 loader 讀什麼、誰應產生或更新它，以及哪個功能真正使用它。不要因為本地 JSON 不存在、設定未填或某個目錄欄位不齊，就直接要求外部商品檔或新增資料服務。

| 需要的內容 | 先檢查的公開介面 | 使用界線 |
| --- | --- | --- |
| 商品識別與目錄 | `Order.contract('dic')` | 核對目錄欄位與各自的更新條件。重複呼叫也可能取得 SDK 快取 |
| 漲停、跌停與參考價 | `Data.get_snapshots(symbols)` | 使用 `limit_up`、`limit_down`、`reference_price`。同物件中的成交價、量與時間各自處理 |
| 分類與限制清單 | `Data.get_table()` → `Data.get(exact_name, *args)` | 核對可用清單、參數、欄位與限制意義。區分成功取得的空表與查詢失敗 |
| 交易單位、信用交易狀態與配額 | `Order.TSECreditInfo(symbol)` | `TradeUnit` 為交易單位股數。核對市場及錯誤碼，並為動態配額設定獨立更新條件 |
| 實際委託、逐筆成交與庫存 | `Account.OrderReport()`、`Account.ExecReport()`、`Account.InventorySum('B')` | 用回報核對各筆委託、執行結果與帳戶庫存 |

沿 API、正規化、快取、規則／狀態機、操作前檢查到畫面，確認在哪一步丟失欄位或判為無效。需要交易行事曆、跳動單位、限制的生效區間或分方向交易資格時，逐項找來源並確認適用範圍。[商品目錄](https://superpy.kgieworld.com.tw/kgipythonapi/guide/tw/orderContract) · [市場快照](https://superpy.kgieworld.com.tw/kgipythonapi/guide/tw/getSnapshots) · [資料目錄](https://superpy.kgieworld.com.tw/kgipythonapi/guide/tw/getTable) · [信用資訊](https://superpy.kgieworld.com.tw/kgipythonapi/guide/tw/orderTSECreditInfo)

## 當日商品資料與 08:00 補查範例

對已確認適合日內沿用的商品／價限資料，以 **Asia/Taipei 當天實際 API 成功取得時間**排定補查。另存來源、資源／商品、上游日期與成功狀態。使用前依該欄位的契約核對適用交易日、市場、價格與單位。商品目錄的 `update_date` 或成交快照的 `datetime` 只有在來源明確定義為規則有效日時，才用來判斷規則的效期。

| 取得與執行狀況 | 行為 |
| --- | --- |
| 當日尚未成功取得 | 向 API 查詢。失敗按該項重試，維持資料待確認 |
| 當日 08:00 前已取得，目前仍未到 08:00 | 保留並使用已成功的當日資料 |
| 當日 08:00 前已取得，目前已到 08:00 | 對這些項目補查一輪。成功後換成新結果，即使值相同也更新成功取得時間 |
| 已於當日 08:00 或之後成功取得 | 在已確認的有效期間內沿用，由資料政策安排下次更新 |
| 已跨本地日 | 以新的本地日期開始取得資料，保留昨日快取的原始日期 |
| 08:00 補查部分失敗 | 保留舊值與來源供追查。等待這輪更新的操作暫待核對，其他成功項目照常使用 |

在每個資源的快取中記錄成功取得的日期與時間，由這些狀態決定是否補查。共同清單可按來源、版本、資源及本地日分組，商品快照再按市場與商品分項。重啟時，依當日成功取得的紀錄判斷是否沿用快取。

已知的處置或暫停區間到點時，可用已取得的有效區間重新判讀。需要涵蓋日內公告變更時，依使用情境另外設定更新方式。08:00 是應用安排補查的時間。上游發布、交易日效力、行情與信用配額各有自己的時間條件。

## 失敗逐項重試，保留成功結果

若應用採用持續恢復政策，暫時失敗的唯讀項目可用 `1, 2, 4, 8, 16, 32, 64, 128, 256, 300` 秒退避，之後每 300 秒重試。成功即停止該輪並將計數歸零。跨日、使用者停止或明確的權限拒絕都應結束該輪，按各自原因處理。

用排程設定下次重試時間，讓帳務處理可繼續。每份清單、每個商品與每種必要訂閱分別保留上次成功結果、失敗原因及下次時間，只補查失敗項目。共同清單尚未取得時，讓依賴該清單的功能等待，其他功能按各自條件繼續。

顯示已執行的重試次數及下次時間。首次查詢失敗但尚未重試時顯示 0，第一次重試失敗後顯示 1。成功後清除舊錯誤並重設為 0。

## 分開日資料、行情與每筆操作條件

| 資料／條件 | 判斷方式 |
| --- | --- |
| 已成功取得的當日商品與價限 | 依上節日政策沿用，避免短 TTL 反覆中斷保護 |
| 最新成交與五檔 | 各自訂閱，保存來源與更新時間。策略若允許沿用最後一筆真實成交，依規則核對整股／零股、試撮、暫停、日期與連線世代，再決定能否使用 |
| 依五檔量判斷的保護 | 用 BidAsk 取得五檔量，保留成功訂閱，只補失敗種類。數量換算依已核對的市場、來源及版本 |
| 目前帳務、原單、可平量與信用額度 | 在相依操作前核對。依各項更新條件查核目前的 `MarignQty` 與 `ShortQty` 配額 |
| 已成交部位的出場資格 | 依出場當時的資格、原委託及可平量查核反向操作。歷史進場資格另作稽核 |
| Live／Observe 與使用者控制 | Live 在已取得正式交易授權且逐筆操作條件都滿足時，才可依策略送撤。Observe 僅監控。畫面顯示目前模式與阻擋操作的具體條件 |

新單依價格或量決策，與撤回已唯一識別的本程式原單，可能需要不同資料。以價限計算的收盤出場，依策略確認是否需要即時成交。為各操作檢查其前置條件，必要時因原單未知、可平量矛盾、不合規的價格或單位，或使用者停止而等待。

暫時缺資料時，顯示等待原因並依重試政策補查。將逾時與使用者主動接手／停止記為不同狀態。使用者的停止狀態應持續到使用者明確解除。

## 帳本與效果仍要逐筆核對

- 每筆成交以帳號、分公司、交易日、市場、整零股及 `OrderNo` 對自己的原委託，再核對商品、方向、類別與累計量。將 `MarketNoN` 保存為市場成交序號，保留回傳的前導零。序號缺失或有矛盾時，保留待核對狀態。[官方成交欄位](https://superpy.kgieworld.com.tw/kgipythonapi/guide/tw/accountExecReport)
- FIFO 是否適用由策略確認。若採同股反向 FIFO，分開現股與信用、日期及市場，保留原始成交並獨立記錄成本分配。核對各筆成交的原單身分，即使商品淨額已歸零。
- 反向成交減少可平量後，核對舊保護單與總預留，必要時先撤回數量不合的單、核實終態再補單，避免部位已平卻留下可成交的出場單。不要直接清空帳本消除差異。
- 查資料失敗可依政策重試。送撤結果未知時，保留原預留並查核原單及成交，避免自動重送。透過委託與成交回報各自確認受理及執行結果。
- 信用當沖與一般信用的列舉值可能不同。依 SDK 版本和委託路徑核對精確拼字與值。SDK 2.1.2 的 7／8 與 3／4 差異及證據界線見[委託說明](orders.md#input-and-report-boundaries)。

## 最小反例與證據界線

採用 08:00 政策時，可用 07:59 成功、08:00 補查、成功後到收盤沿用及跨日重新取得的案例驗證。再檢查失敗項目是否獨立重試、信用配額變更是否影響相依委託，以及商品淨額歸零後仍能發現原委託身分矛盾。

回報驗證結果時，標明使用的 SDK 版本、目標介面，以及證據來自文件、離線回放或券商回報。正式登入、送單與撤單各自需要明確授權。
