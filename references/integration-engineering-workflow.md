# Integration engineering decisions for SuperPy applications

Use this guide when a SuperPy task has a material requirement, data-flow, state,
debugging, verification or delivery question. Read only the relevant part. A
small API query, mechanical edit or known local fix can keep its direct path.
These are engineering decisions, not a mandatory phase sequence or authority
to connect to a broker, publish, restart services or change security policy.

## Establish the useful result

Identify the observable user result, the behavior and strategy to preserve, and
the first effect whose authority or consequences differ from ordinary local
work. Investigate engineering facts directly. Ask only about a material unresolved
product choice or an effect outside current authorization. A proposal-only or
diagnosis-only request keeps that boundary. Reuse current authorization within
its recorded account, effect, time and resource limits.

Treat a checkpoint or intermediate review as an internal handoff when the user
has already authorized the remaining implementation and checks. Continue other
necessary work when one operation is blocked. Stop the affected mechanism on
success, a real blocker or its finite budget; do not invent a successor loop.

## Trace capability through the application

Before declaring a required feed or configuration unavailable, inspect existing
provider capabilities and account methods. For each consequential field, verify
its meaning, unit, identity, target version, entitlement and effective time.
Trace acquisition through normalization, cache, strategy and displayed result.
A product catalog, configured URL or loader does not establish a fresh feed.

When a contract is uncertain, make the smallest authorized read-only or offline
probe that can distinguish the alternatives. Keep unresolved facts local to the
effects that depend on them. Never infer production permission from simulation
failure or from the fact that credentials are present.

## Choose the smallest coherent implementation

Reuse the maintained source and existing boundaries. Check whether a direct call
or small local change can satisfy the result before adding services, wrappers,
state, environments or copies. Split modules where demonstrated responsibility,
latency or change patterns justify it. Respect the project's managed environment,
locked inputs and supported platform; use the chosen Python manager consistently.

When behavior spans modules, identify only the relevant owners: observed facts,
user intent, effect eligibility, operation progress and projections. Follow the
quantities, reservations, time or generations that govern the disputed transition.
Do not adopt a different demo's strategy or missing-data policy by analogy.

## Diagnose before widening the repair

State expected and observed behavior at the failing input or transition. Inspect
the maintained caller, data consumer, guards and the executing instance. Choose
a counterexample that can distinguish the leading explanation from its nearest
alternative. Add only the diagnostics needed to locate the uncertain stage and
correlate an operation with its result; remove credentials from support material.

An uncertain external effect needs reconciliation before a retry. A successful
observation can coexist with missing authority for a later effect. Preserve known
facts and eligible independent work while retaining shared-resource protection.
Preserve dirty work, recovery state and useful reproducers throughout the repair.

## Verify the claim at its real boundary

Use the cheapest check that can falsify the changed behavior. Prefer a
discriminating pre-change regression for a safely reproducible defect. Include a
valid continuation when a guard or recovery change might otherwise pass by
blocking everything. Add SDK-seam, native-host or lifecycle checks only when the
claim depends on them. If an authorized lifecycle test is the smallest useful
experiment, run it directly instead of repeating inconclusive lower-level stages.

For monitoring recovery, check the next real input through subscriptions, account
state, reconciliation and the previously enabled evaluation loop. Preserve user
stops and remaining limits. For an installed app or compiler workflow, inspect
the actual executable/tool result rather than treating static syntax as acceptance.
Do not turn those examples into a whole-lifecycle requirement for a small edit.

Keep source tests, synthetic models, recorded payloads, installed bytes, runtime
observations and publication readback separate. An assistant's report, a tool
call, a green score or a connected indicator does not establish the next layer.
Reuse fresh evidence when the relevant executable bytes and conditions still match.

## Deliver a usable result within scope

State the changed behavior, focused checks, remaining limitations and the next
condition for any blocked effect. Keep the recipient's document free of private
paths, account data and internal planning shorthand. Preserve existing README
positioning and source ownership when updating the skill itself.

When Windows execution or packaging changes, inspect the actual loaded native
payloads and applicable signing evidence. Source tests and a valid launcher
signature do not establish Smart App Control acceptance. Keep local diagnostics
separate from purchases, trust-policy changes, installation or reboot authority.

When one core has multiple enabled consumers, verify the declared compatibility
and state-custody contract for those consumers. Do not assume one successful UI
or channel proves all of them; do not force unrelated modules into one release.
Before retirement or cleanup, establish active use, references, rebuildability,
preservation and task authority. Stop at uncertainty rather than deleting by age.

## Select optional assistance by need

| Need | Useful capability when available | Direct alternative |
| --- | --- | --- |
| Locate a cross-file data or control path | Current CodeGraph index; `codegraph-first-navigation` | Targeted source/caller search and confirmation |
| Resolve material behavior or ownership | `engineering-specification` | Short observable contract and unresolved choices |
| Diagnose an unknown failure | `engineering-debugging` | One hypothesis and discriminating local probe |
| Implement a clear authorized change | `engineering-implementation` | Small coherent change and affected checks |
| Assess recovery, readiness or green-tests/broken-use | `completeness-and-test-synthesis` | Exercise the missing seam or user continuation |
| Preserve a recurring defect | `incident-to-regression` | Minimal redacted fixture and a discriminating check |
| Maintain dependency or candidate boundaries | `modular-evolution`; the project's chosen manager, such as uv for Python | Reuse isolated, locked inputs and inspect active references |
| Assess a Windows delivery claim | `windows-sac-compatibility` | Payload/signature inventory and explicit evidence limits |
| Need genuinely independent bounded work | `baton-fanout-skill`, under current dispatch authority | Main agent works directly when independence adds no value |
| Navigate a long task | Existing project record or optional Context Canvas | Compact source/evidence pointers |

The specification, debugging, implementation, evidence, regression and navigation
names above refer to independently selectable skills in the community
[Smart Agentic Engineering Toolkit](https://github.com/phenomenoner/smart-agentic-engineering-toolkit).
Other entries name tools or separate skills that may be available in the target
environment; their presence is not assumed. Inspect the actual version and
instructions rather than constructing a missing command or installing a dependency.

These capabilities are optional. Inspect their current trigger, availability and
authority before use; do not install them, copy their full rules, dispatch workers
or activate a review chain merely because this guide mentions them. Keep model
and provider choices with the current user and runtime.
