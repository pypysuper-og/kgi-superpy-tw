# 本機 Web OCO 應用設計參考

適用：用 SuperPy 建立本機交易工作台，需要 Web UI、持久化策略部位、登入進度、跨日對帳或可控的程序結束流程時。簡單登入腳本或純行情查詢不必套用整套設計。

本文整理台股本機交易應用的可重用設計，**沒有附上可執行程式、使用者 DB、憑證或原生 log**。下文「範本」指此參考架構，檔名、事件與數值是實作範例，不是 repo 內已提供的模組。可依需求實作並驗證，不假設安裝 skill 就能啟動交易工作台。

這是應用設計經驗，**不是券商官方架構或正式環境保證**。原設計參考 Python 3.13／SDK 2.1.1，手冊基準 v1.37；該應用的執行證據不隨本 repo 發布。API 簽名、成功序列及市場差異仍依 [session](session.md)、[orders](orders.md)、[accounts](accounts.md)。不要直接將台股數量、庫存與撤單規則移植到美股或期貨。

快速定位：下列章節依序為責任分工、命令流程、登入輸出、資料保存、OCO、重連、登出與程序結束、UI、驗證。

## 1. 責任分工與適用範圍

範本為台股現股整張、買進後賣出，每組進場與 OCO 稱為一個 unit。三種模式為 `production`、`simulation`、無網路 `demo`。新專案先依其市場能力與使用者要求選環境；**不得從本參考推定正式環境為預設**，也不要啟動程式就自動登入或交易。

| 檔案／層 | 責任與邊界 |
|---|---|
| `start.cmd`、`run.py` | 啟動一個本機 server，等待自身就緒後開瀏覽器；擁有 Uvicorn 關閉控制 |
| `app/static/` | 表單、快照顯示、命令進度、確認彈窗、說明與分類；不直接呼叫 SDK 或決定成交 |
| `app/server.py` | HTTP 參數與本機來源限制、命令入列、快照讀取、程序鎖及 lifespan |
| `app/service.py` | 單一 actor 執行 SDK 與 SQLite 操作；接收有界命令／回呼 queue、發布快照 |
| `app/engine.py` | unit/OCO、累計成交量、對帳、監控恢復、重連、登出協調 |
| `app/brokers/superpy.py` | 官方公開 SDK 適配及回報正規化；`demo.py` 提供獨立的離線券商帳本 |
| `app/storage.py` | SQLite state、intent、fill、event 與 demo 帳本 |
| `app/login_console.py` | 分段輸出緩衝、遮蔽、登入階段、執行中的可讀快照 |

HTTP 不等待 SDK 完成。SDK 回呼只傳事件，不從回呼直接下單；單一 actor 決定交易效果。此形態適合這個單使用者本機 demo，不代表遠端／多使用者系統可共用同一個無隔離會話。

## 2. 前後端命令與狀態流程

```text
使用者確認操作
  → POST /api/commands/{action}，附 X-Demo-Token
  → HTTP 回覆 command id（只是入列）
  → actor 處理已排入的回呼，再檢查目前交易條件
  → 執行 SDK／更新 DB／發布快照
  → GET /api/commands/{id}：queued → running → done 或 error
  → UI 顯示結果；持續 GET /api/state 顯示委託、成交、unit 與健康狀態
```

- HTTP command id 是短期進度識別，不是券商單號、成交證明或跨重啟冪等鍵；命令結果會淘汰，不是持久化交易帳本。
- SDK 呼叫正常返回也不等於委託成功或成交。UI 超時、HTTP 斷線或 command id 過期不能觸發自動重送 POST；改讀狀態、intent 與券商紀錄。
- 已排入的交易斷線必須先於下一個下單命令生效；不能因 UI 上一次快照仍是 connected 就放行。商品查詢也用請求版本防止舊結果覆蓋新代碼。
- 每次登入遞增 callback generation，略過舊會話回呼。事件 queue 超載時清除可觸價行情並要求對帳，不把遺失回報視為正常。
- 範本命令 queue 64、事件 queue 4096；監控約每 250ms、UI 快照每 700ms、命令結果每 500ms 查詢。這些是本機容量／體驗選擇，**不是 SDK 配額或時效保證**。
- 本機 HTTP 有 Host、同來源 Origin、Sec-Fetch-Site、變更操作 token、CSP 及 no-store；只綁 localhost。這些限制不等於遠端使用者驗證，若改遠端服務要另設身分與會話隔離。

## 3. 登入、帳號與即時輸出

1. 帳號明碼，密碼預設遮蔽並可切換顯示；完成送出流程後清空密碼。帳密不寫 browser storage、DB、命令歷史或應用 log。
2. UI 送 login 命令，由 actor 建立 broker。SDK 匯入、登入初始化、帳戶查詢等階段可即時更新，成功條件依 [session](session.md)，不用私有旗標或「有回傳物件」代替驗證。
3. 列出所有帳號，明示不支援的市場；一個符合範本範圍的證券帳號可自動選，多個由使用者決定。不能默選第一個不符市場的帳號。
4. 選帳後取得其 owner，載入持久化 units/orders，嘗試以可驗證的回報恢復追蹤，再查券商庫存。監控保持暫停，待使用者確認對帳。

登入左側呈現**已遮蔽的 Python stdout/stderr 文字**，不是把有密碼的畫面截圖送出。`LoginConsole` 用獨立鎖提供快照，故 actor 卡在登入時 HTTP 仍能顯示進度；一般交易狀態則可能停在舊快照，要標示未更新。

- 以完整行為遮蔽邊界，不能每次 `write()` 或 `flush()` 就送出未完成行，否則切成兩段的密碼可能外洩。
- 先處理帳戶／驗證欄位，再替換此次帳密，避免密碼剛好是 `token` 等欄位名稱時破壞欄位遮蔽。DOM 用 `textContent` 顯示訊息，不把輸出当 HTML。
- 範本保留最近 400 行；超過 8192 字元的單行整行略過。`finish()` 補尾行並清理暫存敏感值；這不是保證記憶體已安全抹除。
- 本次失敗留在畫面，新嘗試換 attempt id 並清空畫面。即使 HTTP 在建立 attempt 前被拒，也要解鎖表單，不能永遠顯示登入中。
- 遮蔽後的輸出寫 `logs/login-YYYY-MM-DD.jsonl`；若診斷 log 寫入失敗，顯示警告，不能把已接受的券商結果改判失敗而誘發重送。
- `redirect_stdout/stderr` 是程序級重導向；多執行緒／多會話版本不可假設它提供輸出隔離。它也不攔截所有原生 C/C++ 輸出或檔案。
- SDK 2.1.1 的歷史觀察包含寫入 SDK 安裝目錄 `kgisuperpy/pushClient/TradeCom.*.log` 的原生 TradeCom log，檔名可能含身分且遭程序鎖定。設定 runtime 工作目錄不保證所有原生 log 都在那裡。只取已遮蔽的錯誤碼、時間與階段供診斷，不散布原始私密檔案，也不泛化個別登入失敗原因。

## 4. 資料保存、owner 與重新對帳

SQLite 路徑為專案 `runtime/demo.sqlite3`，設定 `journal_mode=WAL`、`synchronous=FULL`，由同一 actor 使用。範本 owner 為環境、分公司、帳號類別、帳號組合的 SHA-256；用於資料分區，**不是使用者驗證、加密或匿名化保證**。

| 表 | 保存內容 | 不可混淆的語意 |
|---|---|---|
| `state` | 每個 owner 的 units/orders 狀態快照 | 不可代替重登入後的券商核對 |
| `intents` | 呼叫券商前落盤的送／撤單意圖與 outcome | `returned` 表示方法返回，不是委託或撤單終態；unknown 禁止自動重播 |
| `fills` | 已確認累計成交量的增量與價格 | 不從庫存差或人工歸屬捏造成交 |
| `events` | 操作、連線、錯誤、對帳調整 | 應用事件，不是完整原生 SDK log |
| `demo` | 獨立展示券商委託／庫存帳本 | 避免拿策略自己的 state 當成「券商核對」 |

成交回報以累計量計算 delta，過濾倒退／超量／異常值；fill 增量與新的累計狀態一起保存。unit 持有量為 `entry_filled - exit_filled + adjustment`。人工調整是獨立的歸屬修正與事件，保留原成交，不修改歷史成交數字。

重新登入、跨日或交易重連時：

1. 暫停自動交易，恢復能證明身分一致的委託。非終態歷史單先標為未對齊；不能只看可能重用的券商單號認領。
2. 查券商現股餘額與可下單量，按股票比較本 demo 的 unit 歸屬。多出庫存只顯示，不自動分配給策略。
3. 可用量足夠且無未知委託／intent時，由使用者確認恢復；按下確認時再次查券商庫存，使用 revision 防止接受舊對帳畫面。
4. 數量不足或結果未明時保持暫停。先核對券商單，再人工調整歸屬並記錄原因；仍可追蹤的有效單不可用「人工結束」直接抹掉。
5. 確認後清舊行情，等待確認時間之後的新鮮 tick。範本没有已證實可自動承接所有跨日訂單的唯一識別契約。

備份使用 SQLite backup API，或停止寫入後保留 DB 與所需 WAL/SHM 一致性；不能只複製活躍主 DB、刪掉 DB 解決對帳差異，或把 DB 隨 skill 發布。

## 5. 成交後 OCO 與 unit 分類

```text
確認進場與 OCO 條件 → intent 落盤 → 送進場單 → 等實際成交
部分／全部成交 → 監控該 unit 的已成交持有量
觸及停損或停利 → 鎖定首次觸發 → 撤剩餘進場
確認進場終態與最後累計量 → 核對可賣量 → 市價 IOC 賣出該 unit
```

- OCO 是本機監控；**沒有預掛停損停利單**。使用者建立 unit 的確認涵蓋後續觸價撤餘單／出場，適用範圍須在 UI 說清楚。
- 平常「撤銷未成交進場」只撤剩餘買单；部分成交的持倉繼續監控。這與「停止監控並撤單後登出」是不同操作。
- 行情必須有效、非試撮且新鮮；範本核對來源與接收時間約 15 秒內。少成交股票的行情過期不直接等同斷線。
- 出場前按券商可賣量與其他本機在途賣單保留量檢查，不足或不明不送單。市價 IOC 部分成交、被拒或未知時保留剩餘部位，轉人工處理，不無限追單。
- 台股數量與庫存換算要沿用已查證契約：本範本整張 order qty 原樣傳入，庫存以明確股數欄位及 `QUNIT=1000` 換算；不能因 UI 寫「張」就自行把所有 API 數量乘 1000。真實欄位與回報仍需券商環境驗證。

分類只篩選畫面，不能改 DB、停止監控或刪除 unit。優先判斷「需處理」，再判斷未結束曝險：

| 分類 | 判斷 |
|---|---|
| 需處理 | manual、負持有量、缺失／未知／未對齊的有效委託、未知 intent，或進場被拒 |
| 進行中 | 仍有持倉，或任一進／出場委託未終結；部分成交撤餘單仍在此 |
| 已完成 | 曾有進場成交，目前無持倉且全部委託終結；人工對帳結束仍保留其獨立標示 |
| 已取消 | 沒有進場成交、無持倉且全部委託終結；拒單不混入此類 |
| 全部 | 所有歷史 unit |

預設顯示全部，各類有數量；切換分類重設分頁，建立新 unit 切回全部。左側是操作中商品，中央涵蓋目前帳號所有商品，寬畫面可並排 unit；不要用操作中代碼篩選中央紀錄。不要用「進場單已取消」就將仍有持倉的整組 unit 視為已取消。

## 6. 連線恢復與監控健康

交易與行情分開顯示 indicator。範本 exponential backoff 間隔為 `1, 2, 4, 8, 16, 30, 30, 30` 秒，最多 8 次；這是可調應用預算，不是券商要求。

交易恢復後重接可驗證的委託並重新對帳；行情重新訂閱返回不等於健康恢復，需等有效 tick，不能因每次方法返回就歸零重試次數。超過預算交給使用者處理。未知送／撤單不隨重連重送；後端阻塞或快照過期要與網路燈號區分。

## 7. 登出、登入前結束與 server shutdown

**此設計允許使用者明確確認後帶持倉登出。** 應用需說明停止監控與保留委託的後果；允許帶持倉登出不代表授權自動平倉或刪單。其他應用應依自己的已確認需求定義此行為。

| 使用者操作 | 行為 |
|---|---|
| 關閉說明、切換 unit 分類 | 不影響監控 |
| 只關網頁 | server 若仍活著，監控繼續；不同於登出 |
| 保留委託並登出 | 確認停止 OCO，不撤單、不平倉；委託仍可能成交，保存部位與紀錄後登出 |
| 先刪單再登出 | 暫停新 OCO，撤本 demo 管理的在途買／賣單，等待所有終態後登出；不處理其他來源下單 |
| 未登入／登入失敗時「結束程式」 | 確認後沿用既有 logout 命令與關閉流程，不另開無保護的 kill endpoint |
| 登入仍執行時「結束程式」 | 排入同一 actor，等登入返回、清理連線再關閉；若期間登入成功，確認內容須涵蓋保留委託／持倉與停止監控 |

刪單後登出需要持續處理回報，不能在 actor 裡以阻塞等待讓回報永遠無法處理。範本 `logout()` 建立 pending 流程、`advance_logout()` 查核終態；此時普通 OCO step 不得再產生新出場單。保存等待期間的晚到成交，既有撤單 intent 不重送。

若撤單失敗、交易斷線、舊日／未知委託無法核對、30 秒未確認所有終態，或 SDK logout 出錯：**不宣稱已登出、不啟動成功關閉**；保留服務、顯示原因並保持監控暫停，核對後再確認恢復。30 秒限制是回報等待預算，無法強制中斷已阻塞的原生 SDK 呼叫。

成功關閉順序：

1. 保存當前 units/orders，SDK logout 成功；清除記憶體登入狀態，歷史 DB 保留。
2. 發布命令 `done` 及 `server_shutdown: true`，設定 service closing；HTTP 入列與 actor 執行兩處拒收後續工作，包含已排隊的新操作。
3. UI 讀到成功結果後停止輪詢、停用控制、顯示程式已結束。避免 `logout → 再 refresh → server 已關閉` 被誤報成登出失敗。
4. `/api/commands/{id}` 的成功回應送出後，以 background callback 設定該 runner 的 `server.should_exit=True`；`run.py` 另在看到 closing 後等 5 秒啟動關閉，處理頁面離開而未讀結果的情況。
5. lifespan 停止 actor，保存／關 DB；actor 確認終止才釋放 instance lock。若仍阻塞就保持鎖直到程序結束，不另啟第二個交易 owner 繞過。

`api.logout()` 本身不會停止 Uvicorn。自動停止能力來自 `run.py` 傳入的 callback 與 closing watcher；單獨 `uvicorn app.server:app` 沒有同等程序結束語意。也不要按任意 port/PID 殺程序或用 `os._exit()` 代替正常收尾。

`start.cmd` 透過 `start.vbs` 隱藏啟動 `start.ps1`，再以專案 venv 的 `pythonw.exe launch.pyw` 呼叫 `run.serve(open_browser=True)`。失敗用提示框與應用 log 呈現，前景診斷仍可執行 `python run.py`。runner 只在**自己**的 server ready 後開瀏覽器，不靠固定睡眠或看到同 port 有 listener 就假設成功。單 worker、無 reload，避免多個 actor 重複監控交易；runtime 的 OS 檔案鎖不是僅靠「鎖檔存在」判定。

## 8. UI 與可讀性

登入用等高双欄：左側逐行輸出，右側表單。成功後的商品、下單、units、委託、成交、事件盡量在同一畫面；帳號、對帳、交易確認、操作說明用彈窗。正文以功能說明為主，避免佔空間的宣告標語。

範本主要輸入 16px、unit 數字 21px、委託內容 14px。可見空間不足時減少每頁筆數，避免縮成難讀的小字；檢查實際 button bounding box 及面板 scroll 尺寸，**不能只因 body 無 scrollbar 就說沒有裁切**。分類保留原始狀態、錯誤與人工對帳標示。

操作／結果可追查設計另見 [診斷 log 與支援指南](diagnostics-support.md)：run_id、command_id、開始／終止、委託狀態轉換、敏感值排除、支援封裝及 agent 判讀順序。隱藏 console 不表示可以省略這些證據。

## 9. 實作時的驗證方式與界線

依修改範圍選下列最小必要檢查，不必每次重跑全部，也不要為了測 UI 自動登入正式券商。

| 要驗證的行為 | 建議的驗證方式 |
|---|---|
| 部分成交、取消仍保護、OCO、未知結果、對帳 | 用假券商回報重現事件順序，核對部位與 intent |
| stdout 分段遮蔽、阻塞時仍有進度、HTTP 拒絕解鎖 | 分段輸出測試與瀏覽器互動檢查 |
| 登出確認、撤單終態、晚到成交、失敗不關閉 | 用假券商注入晚到事件及撤單失敗 |
| 真實本機程序退出、port 與鎖釋放、DB 可再開 | 啟動隔離的本機程序，確認結束與資源釋放 |
