# 交易應用 UIUX 設計指南

適用於使用 SuperPy 開發或改善行情工具、人工交易介面、策略工作台與自動執行程式。本文提供可組合的互動模式；策略、委託方式、監控條件與復原政策由使用者的產品需求決定。純 API 問答、簡單腳本或回測計算不必加入這些畫面。

這是社群整理的應用設計建議，不是券商官方介面規格、可直接執行的產品或投資策略建議。可重用的是資訊與互動結構；市場 API、數量單位、可交易條件及帳務語意仍須依各市場參考確認。

快速定位：需求邊界 → 狀態呈現 → 操作回饋 → 可組合畫面 → 提醒與復原 → 情境驗證。具體案例見 [本機 Web OCO](web-oco-application.md)，操作追查見 [診斷與支援](diagnostics-support.md)。

## 1. 先確認產品要讓使用者做什麼

從已有需求、原始碼與畫面確認下列事項；只詢問會影響實作的缺口，不要求使用者填完整問卷。

| 要釐清的邊界 | 如何影響介面 |
| --- | --- |
| 行情觀察、決策提醒、人工送單或自動執行 | 決定是否需要交易確認、執行權限與停止操作 |
| 市場、帳戶、商品及數量單位 | 決定標示、欄位、價格精度與可用委託方式 |
| 策略依據：成交、報價、時間、部位或其他訊號 | 決定資料來源、有效性條件與下一次動作的說明 |
| 執行位置：瀏覽器、本機背景程序或遠端服務 | 決定關閉頁面、睡眠、斷線與登出的實際影響 |
| 一個或多個策略／帳戶 | 決定總覽、篩選、操作範圍與切換時的提示 |

採用能回答使用者問題的最小畫面。不要因為有 OCO 案例，就加上停損停利、固定三欄、SQLite、單一 actor、15 秒門檻或重啟後一律人工確認。

## 2. 分開呈現各種狀態

單一綠燈無法證明策略正在有效執行。依應用需要分開呈現下列資訊，再用簡短摘要說明當前影響。

| 狀態面向 | 使用者需要知道 | 不能據此推定 |
| --- | --- | --- |
| 環境與身分 | 正式／模擬／展示、目前帳戶與操作對象 | 有登入就有該市場的交易能力 |
| 連線與服務 | 交易連線、行情連線、後端快照是否更新 | 通道連上就有該商品資料 |
| 資料 | 來源／交易別、最後有效資料、時間與有效性 | 訂閱成功就已收到第一筆資料 |
| 策略 | 等待條件、執行中、暫停、完成或需處理 | 有持倉就一定正在監控 |
| 執行模式 | 只觀察、僅提醒、待確認或允許自動執行 | 收到訊號就一定會送單 |
| 委託與成交 | 受理、未成交、部分成交、終態與結果未明 | 方法返回、撤單請求或逾時等於終態 |

狀態須由後端可證實的資料產生；前端不能因請求成功或收到連線事件就自行推定成交或有效監控。資料失效時，保留最後值並明示時間與不可用原因，避免舊數字看起來仍是即時資料。

行情依賴應跟隨實際消費者：例如既有策略、持倉監控或行情頁。若背景策略需要資料，登入載入或重連時應依其生命週期恢復所需訂閱，不依賴使用者重新查商品；切換左側商品也不應中斷其他策略的資料。僅查行情的工具則可按畫面需求訂閱，避免無人使用的訂閱長期占用配額。參數及配額見 [行情參考](quotes.md)。

詳情可列出「需要此資料的策略」「訂閱請求／確認時間」「首筆／最近有效資料時間」。拿不到的欄位標成未知或未記錄，不用現在時間補造。無新成交、資料過期與網路斷線要分開；有效性門檻依資料種類及策略定義，不能統一套用成交 tick 的時間門檻。

## 互動登入的必要回饋

當產品提供 SuperPy 互動登入（Web 彈窗、桌面 GUI 或工作台）時，登入期間必須有可動態展示實際 SDK screen output 的區域；只有「處理中」文字、轉圈或返回後一次顯示摘要不足以滿足此需求。純 API 解說、無互動登入的腳本不必因此加入 GUI。

- 在第一次 SDK 登入呼叫前啟用輸出捕捉；串流完整行並遮蔽帳密、身分證、帳號、Token、URL 查詢參數。分段 write／flush 不得造成半段密碼外洩；限制行長、記憶體歷史及 UI 高度。只使用文字節點呈現，不能把 SDK 輸出當成 HTML。
- Web 輸出通道須獨立於可能阻塞的 SDK 執行緒。登入尚未返回時，輪詢或串流仍須能取得新行；不要把進度查詢排到同一個阻塞中的工作佇列後面。SDK 或原生元件無法攔截的輸出須明示覆蓋範圍，不能偽造進度。
- 將「登入 → 明確選帳 → 完成」做成可見的階段切換。登入成功後改顯示選帳畫面，不自動選第一個帳戶；選帳成功才關閉登入彈窗。錯誤留在相應階段，供查核與重試。
- 主畫面分別標示本機後端、正式／模擬券商會話、所選帳戶及實單權限；本機 HTTP 正常不能代表券商已登入。成功判據遵循 [Session](session.md) 公開登入序列與帳戶查詢，並說明狀態依據；不虛構額外心跳 API。
- 重連使用可取消的退避排程；次數及上限由產品政策決定。若使用者明確要求持續重連，允許有延遲上限的不限次數重連，仍須在登出／程式結束時停止。保留精確帳戶身分並對帳，不因重連重送未知委託或默默恢復交易權限。
- 使用者要求結束程式時，先完成委託處置與券商登出，再關閉後端。只有取得登出／關閉確認才顯示全畫面「程式已結束，可以關閉視窗」；單純網路中斷或畫面逾時須顯示結果未明。

最小驗證情境：延遲 SDK 登入時畫面已顯示新輸出；分段敏感資料被遮蔽；成功後切換選帳；選錯或初始化失敗不誤關視窗；成功選帳後主畫面顯示所選帳戶；登出失敗不顯示程式已結束。測試替身可驗證 UI／執行緒接線，正式連線成功仍需另外的已授權實測證據。

## 3. 讓操作範圍與結果可理解

- **送出前：** 在操作附近顯示環境、帳戶、商品、方向、數量單位及執行方式。對真實交易、批次操作或會改變自動執行權限的動作，依影響提供確認摘要；純查詢與篩選不需要重複確認。
- **處理中：** 顯示已接收、處理階段與等待對象，防止同一操作重複提交。進度只能反映已知階段，沒有可估計時程就不用假百分比。
- **完成後：** 區分應用命令完成、券商受理與實際成交。對結果未明的操作，提供查核狀態與關聯紀錄的入口，不把重新送單當成通用復原按鈕。
- **無法操作：** 按鈕旁顯示主要原因與下一步，例如「等待有效行情」「請先選帳戶」。詳細原因可以展開，不只用灰色或滑鼠提示；前端停用仍須配合後端當下的檢查。
- **失敗後：** 保留可安全保留的輸入，指出需修正欄位；不要保留密碼，也不要以清空整張表單處理單一錯誤。

停止策略、停止建立新委託、取消未成交單、平倉與登出，各自說明對既有委託、持倉及後續自動動作的影響。若是批次操作，列明作用範圍與個別結果，保留成功、失敗及未知項目，避免整批按一次「重試」造成重複交易。

## 4. 按需要組合介面

| 模式 | 適合呈現什麼 | 使用界線 |
| --- | --- | --- |
| 登入與初始化進度 | 已完成階段、目前等待、可採取的動作 | 遮蔽敏感內容；一般使用者先看摘要，診斷輸出可展開 |
| 商品與資料區 | 操作中商品、交易別、數量單位、有效行情 | 明示此區與全帳戶／其他策略清單的篩選關係 |
| 策略卡片或表格 | 識別、狀態、關鍵參數、執行方式、最近事件及可用操作 | 策略多時採摘要與詳情；卡片不固定塞滿所有參數 |
| 委託／成交紀錄 | 執行進度與實際結果 | 可按策略追查，也可查看全帳戶；範圍需明示 |
| 事件與提醒區 | 需注意的變化、時間、對象與後續動作 | 不讓一般連線訊息淹沒交易異常；原始 log 放診斷層 |
| 說明／詳情 | 原因、影響、目前處置、使用者下一步 | 不遮住長時間必須監看的關鍵狀態；關閉說明不應暗中停止策略 |

策略摘要可沿用「識別 → 狀態 → 條件 → 執行方式 → 最近事件 → 操作」的資訊順序，名稱採使用者熟悉的產品語言，不必叫 unit。

| 示例需求 | 摘要可顯示 | 由該產品自行定義 |
| --- | --- | --- |
| 條件式出場 | 部位、觸發條件、行情、出場方式 | 觸發後撤餘單、送單與部分成交處理 |
| 定期買入 | 金額／數量、排程、時區、下次執行時間 | 非交易日、錯過排程及重啟後是否補執行 |
| 網格策略 | 區間、格數、在途委託與策略部位 | 掛單配置、重新定價、停止與退出方式 |
| 人工交易或純行情 | 操作商品、資料、手動委託或觀察清單 | 可完全沒有策略卡片與自動執行按鈕 |

以上是資訊設計示例，不表示 SDK 提供上述策略或排程 API。

桌面可用並排區域，窄畫面可用分頁或詳情抽屜。保留重要數字、單位及操作的可讀性；資料多時分頁、篩選或摘要，不以縮小文字解決全部空間問題。分頁與篩選只改變顯示，不應改變策略生命週期。總覽的「執行中」「有部位」「未結束」需各有一致計數定義。

顏色搭配文字或圖示，不只依紅綠判讀；金額與數量明示單位並對齊。確認視窗應可用鍵盤操作、有標題、返回路徑及關閉後的合理焦點。重要原因與操作不可只靠 hover 才能看見。開發參數與內部識別碼放詳情，避免佔據主要交易流程。

## 5. 提醒與復原也屬於產品流程

**提醒：** 明示觸發對象、條件、資料時間、事件時間，以及是否已產生交易動作。短暫提示可作為補充；需要後續處理的事件應有可再次查看的紀錄。多筆同時到達時保留各筆，重新開頁面要區分新事件與歷史事件。已讀只代表使用者看過，不代表交易問題已解決。

提醒去重、重複頻率與升級方式依策略決定，例如只提醒一次或條件重新成立再提醒；不要默認所有策略都採一次性通知。畫面提示、聲音、瀏覽器通知與外部推播有不同可達條件，僅承諾實際提供的管道；關閉頁面後仍有後端紀錄不代表使用者會收到通知。

**降級：** 資料不足、庫存／可交易量不符或外部操作未明時，說明受到影響的功能與仍可使用的功能。「僅提醒」可以是一種策略明確支援的降級方式，不能只改 UI 標籤就宣稱它安全可用。查詢失敗、查無資料與已確認數量為零要分開；保留已確認成交，不用帳務暫時缺資料推定未成交。

**恢復：** 重啟或重連後，呈現已載入的策略、已恢復的資料、待核對事項及目前執行權限。是否自動恢復、需使用者確認、等待新訊號或補執行，依原有策略契約與授權決定；若需確認，按下時重新檢查相關條件。復原不能暗中重送結果未明的委託。

## 6. 用使用者問題驗證設計

選擇與此次變更相關的情境即可。使用展示資料、受控回報或隔離測試服務；設計或測試 UI 不授權登入正式環境與交易。

| 情境 | 應可直接從介面判斷 |
| --- | --- |
| 登入或 SDK 呼叫很慢 | 正在等待什麼、資料是否仍更新、可以安全做什麼 |
| 訂閱確認但尚無有效資料 | 已訂閱與已收到資料的差別，策略是否具備執行條件 |
| 切換商品或策略分類 | 當前操作範圍，以及其他策略仍保有原本狀態 |
| 部分成交、取消請求或結果未明 | 哪些已確認、哪些仍在等待，持倉與委託沒有被誤判結束 |
| 觸發提醒或自動動作 | 依據哪個條件、是否送單、後續結果在哪裡查 |
| 重啟後尚未手動查商品 | 已有策略是否恢復所需資料，還有哪些條件阻擋執行 |
| 多筆提醒與再次開啟畫面 | 事件不遺失，新提醒與歷史紀錄可區分 |
| 關閉頁面、停止策略或登出 | 哪些監控會停止、哪些委託仍可能執行 |
| 目標視窗尺寸、縮放與鍵盤操作 | 關鍵按鈕、原因與數字可見且可操作，彈窗焦點可返回 |

檢查實際元件邊界、面板捲動與操作結果，不能只因頁面沒有 scrollbar 就宣稱沒有裁切。若提出的是尚未實作的畫面，標明為建議；若已測試，列明情境、環境與觀察結果。展示驗證、正式資料接收與真實交易驗收是不同證據。
