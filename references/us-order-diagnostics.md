# 複委託委託查核與非同步回報

適用美股 `SubOrder`／`SubAccount`。公開欄位以使用手冊 v1.37 為基線；下列 SDK 內部行為由 2.1.2 原始碼核對，屬版本特定觀察，不代表其他版本保證。不得直接操作 SDK 私有快取或底層元件來繞過公開 API。

## 查哪一個來源

| 來源 | 可回答的問題 | 限制 |
| --- | --- | --- |
| `SubOrder.set_event(callback)` | 本次會話收到哪些委託／成交事件？ | 先註冊再下單；斷線、晚到、重複事件需處理。收到事件不等於應用已成功配對或入帳 |
| `SubOrder.get_trades(full=True)` | SDK 目前追蹤哪些 Trade，包括終態？ | 2.1.2 返回 SDK 記憶體快取；方法成功不是一次完整券商查詢，空結果不是「原單未送達」證據 |
| `SubAccount.OrderReport()` | 券商委託序號、處理狀態、拒單代碼／原因、累計成交？ | 返回 DataFrame；查詢可能逾時，欄位需核對。只取需要的欄位，勿輸出整張含姓名／帳號／IP 的表 |
| `SubAccount.ExecReport()` | 哪個委託有成交，成交量、價格與來源日期？ | 以確定的委託身分連結；日期／時區仍要核對，不因查詢成功就直接入帳 |
| `SubAccount.StockPositionReport()` | 帳戶持股可否佐證？ | 庫存不能單獨證明某一筆本地委託已成交；Qty 也不是可賣量保證 |

在已授權、已登入且明確選定的複委託帳戶會話中，唯讀查詢範例：

```python
frame = api.SubAccount.OrderReport()
columns = [
    "symbol", "BuySell", "qty", "price", "seqnum", "orig_seqnum", "orderno",
    "action", "sales_status", "sales_status_code", "order_err_code", "order_err_msg",
    "exe_qty", "exe_avg_price", "exe_status_code", "trade_date", "create_time",
]
rows = frame.reindex(columns=columns).to_dict("records")
# 先依帳戶、商品與委託身分限制展示範圍，再遮蔽敏感訊息；不要 print(frame)。
```

工具應透過原本擁有 SDK 的執行緒查詢，避免第二次登入或跨執行緒操作 SDK。查詢失敗須顯示「未取得」，不能當成空單或授權重送。展示查詢時間、來源、資料截斷與未知欄位；唯讀診斷不應暗中確認對帳、認領外部委託或改帳。

## 建立可追溯的委託識別

送單前持久保存本地 intent 與唯一 `name`。保留 create_order 返回的 `Trade`，再追蹤後續補上的 `order.org_seqnum`（原始委託序號）與 `order.order_id`（成功後的單號）。不能只複製方法返回當下的空識別後丟棄 Trade。

- `name` 是輔助關聯；2.1.2 的策略名稱回報有自己的更新路徑，不保證與委託事件同時抵達。
- 2.1.2 的 `Operation.nid` 初始為請求識別，後續可能改成委託序號；應保留各階段觀察，不能當作永不改變的唯一鍵。非 Deal 事件 `seqno` 與 Deal 的 `order_id` 不可互換。
- `org_seqnum`（Order／Event）對應 `orig_seqnum`（OrderReport）；保留原值與來源。已確認且帳戶範圍相同的原始序號可用於配對，不要求拒單一定有成功單號。
- 限定帳戶、會話世代與本地歸屬；校驗商品、方向、數量及既有單號是否衝突。禁止僅憑同商品、同價同量或時間接近自動認領；一個券商委託不能分配給兩個本地 intent。
- 處理 callback 先於方法返回、單號晚到、名稱缺失、重複／亂序事件與重連。新單正常等候可設有限寬限期；等待期間仍保留資金／股數及一單限制，不自動重送。超時只表示結果待核對。
- 原始識別可先保存；缺少可核對的成交量價時保留未入帳原因。只有來源時間／時區不足時，分開標示日期品質，不因此否決已確認的成交量價；詳見下方「成交時間與報表品質」。

若舊版已遺失本地 intent 與 SDK 請求的關聯，完整報表可補充人工查核證據，但不保證能自動恢復一對一關係。重啟不能還原已丟失的記憶體關聯。無確定身分時保留未知，交由明確、可稽核的對帳流程處理。

## 拒單狀態、原因與 errMsg.ini

三類資訊應分開保存與展示：

1. `sales_status_code` 是委託處理狀態，例如 `2` 委託成功、`3` 委託失敗；不是具體拒單原因。
2. `order_err_code` 與 `order_err_msg` 是委託錯誤代碼與券商原因；保留原始值。`exe_status_code` 是成交狀態：0 未成交、1 部分成交、2 全部成交。
3. `errMsg.ini` 是共用錯誤說明字典，不是個別委託紀錄，也不保證所有複委託上手原因都有對照。

2.1.2 的 `CA.load_errmsg()` 讀目前工作目錄下 UTF-8 `errMsg.ini`，以 `key=value` 建表；重複 key 後者覆蓋前者。`SubOrder._OnOrderReport` 用錯誤碼中的數字查字典，再加上 `ORDER_ERR_MSG`，放入 `Event.msg` 與 `Operation.msg`。Pending 路徑使用其 `ErrMsg`。這些是解讀來源的依據，不是呼叫私有方法的建議。

應用應保存經遮蔽的 callback `task/status/seqno/org_seqnum/order_id/msg`、接收時間及關聯識別；再由 OrderReport 補足結構化錯誤碼。Event 欄位表沒有保證獨立 `error_code`，不可自行虛構。查不到 INI 時仍展示原始碼／原因；保留 INI 版本或內容雜湊、同碼歧義，不把推測的「資金不足」當成實際拒單原因。行情 D500 等錯誤不等於委託拒絕原因。

注意 2.1.2 可能把拒絕新單的 Trade 整體狀態設為 `Cancelled`；核對 NewOrder operation／事件與報表原因，勿把拒單一律顯示成使用者撤單。成交依實際 Deal／成交報表與累計量核對；部分成交後終止不能當成零成交拒單。

## 從症狀到處理的查核流程

適用「沒有回報」「結果未明」「看似拒單卻不能重送」「重啟後無法對帳」。只問 API 簽名或查看已確定終態時，直接讀對應資料，不必啟動完整診斷。以下是應用設計流程，不授權 agent 操作實單。

1. **固定查核對象。** 確認 SDK 版本、執行版本、環境、選定帳戶、本地 intent、商品與送單時間。先看是否真的呼叫 SDK；本地驗證拒絕、HTTP 逾時、SDK 返回及券商拒單分開處理。策略目前設定不能替代送單當時參數。
2. **對照四層證據。** 查看已遮蔽 callback、返回的 Trade／SDK cache、OrderReport、應用帳本。檢查 callback 是否註冊、是否進入正確會話世代、收到後是否配對、持久化及更新畫面。單號配對成功只證明身分關聯，不代表狀態欄位已完整。
3. **缺失時查完整報表。** 若已知原始序號，但快取不存在或唯一快取的狀態仍空白／未知，透過相同 SDK owner 補查 OrderReport。先按目標原始序號限制報表，再依成交累計決定是否需要 ExecReport；別讓不相關的歷史成交查詢失敗擋住零成交拒單的確認。
4. **確認身分與內容。** 自動套用需同帳戶、可靠原始識別且唯一，商品、方向、原始量價與已有單號不可矛盾。一筆完整報表應取代同一原單的空白快取觀察，不要把兩者串接成兩筆候選而誤判歧義。身分衝突或多筆互斥報表不能靠「較新」或「最後一筆」消除。
5. **更新已確認事實。** 確認零成交新單被拒後，持久保存終態、錯誤碼與原因，再釋放該未成交預留。已確認終態不被後續空白／處理中快取覆寫；若晚到資料有新增成交、累計倒退、改單歷程或矛盾，重新查核，不能忽略有效的新證據。成交增量只入帳一次。
6. **讓使用者完成下一步。** 顯示「已確認拒單」「查詢失敗」「尚未配對」等具體結果及原因。已拒單提供受條件限制的重送；未知提供查單／配對；需要登入、實單設定或對帳時直接導引到相應視窗，完成返回原操作。

一次人工診斷可先取一份快取與一組報表；僅在暫時查詢錯誤或新事件提供新證據時補查一次。仍不足便回報缺少哪個欄位／來源，保留未知並停止該次診斷。這個有限查核預算不取代產品已授權的背景監控；背景補查沿用有速率限制的追蹤排程，未結訂單解決、登出或關閉時停止相應追蹤。網路重連不等於交易重送。

### 常見情境與分流

| 觀察 | 判斷與下一步 | 不能推論 |
| --- | --- | --- |
| create 返回空單號；稍後 callback 有識別 | 保留 intent 與 Trade，依可靠關聯補綁識別，持續查核狀態 | 返回空值代表沒有送出 |
| 原始序號相符，cache 狀態空白；callback 先拒單再處理中 | 查完整 OrderReport，核對新單操作、零成交及拒單碼；不能只按 callback 到達順序決定終態 | callback 缺少 msg 代表沒有錯誤 |
| OrderReport 新單失敗、零成交、沒有成功單號 | 以原始序號確認拒單，保存碼與原因；對帳後可明確確認新委託 | 沒有成功單號就不能確認拒單 |
| `order_err_code=20095`，`order_err_msg=30003 圈存處理失敗` | 保存這組版本／案例觀察；比對實際送單結算、帳戶與券商可用資金資訊，必要時向券商詢問 | 直接把代碼固定解釋成美元不足、台幣不足或匯率問題 |
| 券商 App 有持股，本地仍為零 | 取得原始識別、OrderReport／ExecReport，確認歸屬與量價後入帳 | 持股增加一定來自這筆 intent |
| 委託有部分成交後撤銷／失敗 | 已確認成交照實入帳，剩餘量依終態處理，按策略政策核對部位 | 等同零成交拒單，可原量重送 |
| 已配對在途單不在重啟後的 SDK cache | 以已保存識別追蹤完整報表，保留一單限制；可恢復追蹤但不重送 | cache 空白代表券商沒有在途單 |
| 同量價多筆、識別互斥、查詢逾時 | 保留未知，提供候選／錯誤與人工核對入口 | 查不到就是失敗或已撤銷 |

20095／30003 是去識別化實際案例的回報組合，不是完整官方錯誤碼目錄。另一商品成功而此商品失敗時，比較真正送出的 `action/symbol/qty/price/currency/name`、帳戶及時序；策略的單筆／每日上限可能只影響本地驗證，不一定傳給 SDK。同路徑採不同結算方式值得查核，但相關性不能證明圈存失敗的底層原因。

## 自動配對、人工確認與恢復

- **自動可確定的先完成。** 對既有可信身分關聯，可按產品契約自動追蹤並更新狀態；缺少關聯時，商品、方向、量價與時間只形成候選。候選唯一也不必然是身分證據，不可默默認領外部單。
- **人工配對先預覽。** 展示本地原單、候選原始序號／成功單號、方向、量價、成交累計、來源時間與錯誤，標示「身分已確認」或「建議／需人工確認」。無唯一候選保持未選；一個券商委託只能分配一次。
- **確認時查新狀態。** 預覽綁帳戶／會話、策略版本、本地委託及券商快照，設有限有效期。使用者確認時重查，有實質變化就更新預覽；不要套用過期配對。用原子交易保存配對、成交增量與庫存核對，失敗保留可重查狀態。
- **只阻擋受影響策略。** 核對同帳戶同商品已分配部位，避免總分配超過已確認持股；不能把全部帳戶持股直接灌進單一策略。某策略缺資料不阻擋另一個身分／部位已確認的策略。已確認在途單可以恢復追蹤，但不允許同策略新增衝突委託。
- **完成後離開流程。** 批次恢復全數成功可關窗並提示；部分失敗保留未完成清單與原因。登入後可詢問是否恢復監控、主畫面可提供全部啟動／停止；恢復授權依原產品契約，不把登入成功視為新單授權。

## 成交時間與報表品質

先找有文件或實際欄位證據的 epoch timestamp／含 offset 時間；核對秒或毫秒及欄位語意，不能把十四碼日期字串當成 Unix timestamp。來源沒有時區時保留原字串，標示未知，不要求使用者猜來源時區。

確定身分、成交量價與庫存歸屬後，**日期／時區缺失本身不應阻擋成交入帳或恢復監控**。分開保存原始來源時間、接收時間、時間品質與來源；無法確認日期時可用接收順序作暫估成本，但不能冒充確切成交時間。量價、身分或成交累計不足仍需補查，不用委託均價或行情猜成交。

日報不得把未知日期成交強塞入任一天；顯示未定日期的量額，若可能影響單日損益或成本順序則標記未知／暫估。產品可明定每日預算按接收日暫計以免漏算，但報表日期與風控日期要分開。後續來源時間補正須保留更正歷程、重算受影響報表，不靜默覆寫歷史；期初成本未知也不當成零。

## 結算方式調整與送單稽核

`Currency.TWD` 是台幣結算，`Currency.MUT` 是外幣結算；不能把 MUT 本身當成所有商品固定的 ISO 幣別。比較兩筆交易時，結算方式與帳戶和量價同樣需要核對。無論 UI 是否允許修改，都保存**實際送單當下**的值。

若策略支援修改結算方式，建議先停止新單並處理在途／未知單，再以目前版本儲存；新設定只影響後續新單，不改原單、不改成交歸屬。每筆 intent／委託保存結算快照，送 SDK 使用該快照；只改結算方式不應重設無關的網格基準或持股。拒單後重送確認同時展示原單及新單結算設定，建立新的 intent。

舊帳本回填只有在能證明舊版該設定不可修改、或有送單／版本歷程時才採來源值；否則標未知。遷移原子完成且可重啟，不在每次啟動用目前設定重標所有歷史。

報表分開「目前策略設定」「每筆送單結算」「交易／成本記帳幣別」。例如以美元移動加權成本計算的美股策略，跨 TWD／MUT 仍以相同 USD 成交量額維護部位，可按歷史結算方式彙總交易量額；沒有匯率、實際扣款與費用證據就不產生台幣成本／損益。不把兩種結算來源的同商品部位拆成憑空獨立的成本帳。

SDK 呼叫前記錄白名單參數與 order intent 關聯：symbol、action／side、quantity、price、settlement、client reference、策略版本、帳戶分區。返回、callback、補查、配對、成交、重送的前後 intent 及查核理由要能串起來。`call_started(parameters={})` 或目前策略設定無法證明歷史送單參數；明示證據缺口。公開參考資料只保留去識別化情境，不能附帳號、原單號、私有 log、DB 或憑證。

## 撤單、結束與手動重新送單

- 撤單使用 `SubOrder.cancel_order(org_seq)`。缺原始序號時顯示「未送出撤單」；方法返回只代表請求返回，必須等券商終態或查報表。原單可能已成交，撤單失敗不會撤銷成交。
- 分開記錄「未送出」「請求已送出、未確認」「券商拒絕」「已確認撤銷」「已成交」。不把 pending/timeout 當撤單成功，也不因重複點擊而重送結果未明的撤單。
- 使用者選擇在撤單未確認時結束，可停止新單、保存未結清單、登出並正常關閉；全畫面提示「程式已結束」同時逐筆列出需至券商手動查核的商品、方向、量價、已知識別與原因。程式結束與券商撤單成功是兩個不同結果；登出／後端終止本身失敗仍須如實標示。
- 「重新送單」必須是使用者明確確認後建立新的 intent，保留與原拒單的關聯。僅對已確定拒絕、零成交、無未知／在途衝突的原單開放；重新核對帳戶、對帳、實單授權、行情時效、盤別、價格股數與資金／庫存限制。原單仍未知或已部分成交時不直接重送。

## 依變更選擇驗證情境

用假 SDK 與隔離帳本重現：返回空識別後回報晚到、callback 先到、name 不回傳、拒單無成功單號、重複／衝突回報、重連的舊事件、查詢逾時、INI 缺失、撤單未確認後結束、拒單後重試建立唯一新 intent。UI 驗證查單入口、錯誤文字、對帳導引及結束清單；本地通過不能宣稱正式券商查詢或成交已驗證。


| 修復範圍 | 假 SDK／隔離帳本應驗證的結果 |
| --- | --- |
